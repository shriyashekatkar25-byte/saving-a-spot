Saving a spot, and knowing when to let it go.

A paused change-data-capture pipeline keeps a replication slot open on the customer's PostgreSQL database. Every hour it stays away, the database hoards more write-ahead log. How long should the default guard wait before it drops the slot?

01 · The decision

One default, two ways to hurt a customer

Customer problem

The slot that waits forever

The new integrated pipeline removes the always-on gateway and can run on a schedule. Between runs, and whenever a run fails or someone pauses it, PostgreSQL keeps every change since the last read so nothing is lost. A forgotten pipeline can quietly fill the production database's disk.

Proposed change

A default slot guard

Ship every integrated pipeline with a guard that drops its replication slot once the pipeline has been absent for H hours. The source is protected; the price is a full refresh (re-snapshot) when the pipeline comes back late.

The pipeline can't measure the source while it's stopped, so the guard is time-based by design.

Success metric

Thirty quiet days

Share of integrated CDC pipelines that run 30 days with no manual slot intervention and no source-disk incident. Target: 97%+.

Guardrails

Lines we don't cross

Source disk-full incidents≤ 2 / 1,000 pipeline-months
Forced full refreshes≤ 60 / 1,000
Re-snapshot hours≤ 400 / 1,000
Data loss from dropped slots0 (always re-snapshot)
Stakeholders

Who's in the room

  • Customer DBAs who own the source disk
  • Data engineers who own freshness
  • Ingestion engineering (connector + cleanup tooling)
  • Support, who field the 2 a.m. "disk full" ticket
  • Field teams selling the move off the gateway

04 · The math, from my Monte Carlo course

Inverse CDF: turning a coin into a clock

Continuous

Away time is exponential

If outages end at a steady hazard, away time T has CDF F(t) = 1 − e−t/μ. Solve F(t) = u for t and every uniform number becomes a duration:

T = −μ · ln(1 − U)

A maintenance pause (μ = 3 h) and a forgotten pipeline (μ = 300 h) use the same line of code with different μ.

Counts

How many stops per month

Stops in a month follow a geometric count: each "chance to stop" fails with probability 1 − p. Inverting its CDF gives

K = ⌊ ln U / ln(1 − p) ⌋

so one uniform draw tells me 0, 1, 2… stops without looping.

Discrete tables

Who is the customer?

Write-rate tier and free-disk tier come from a joint 3×3 table. Lay the nine cell probabilities end to end on [0,1], draw U, and pick the cell it lands in. The stop's cause (pause, credentials, network, forgotten) uses the same partition trick.

Why it matters

Common random numbers

Every guard setting is scored on the same sampled stops, so the cost curve compares policies, not luck. Rates shrink like 1/√n: at 8,000 pipeline-months the disk-full rate carries roughly ±1 per 1,000 of noise.

05 · How I'd run it on real data

From telemetry to a default

SQL: fit the inputs

-- illustrative tables
WITH stops AS (
  SELECT pipeline_id, stop_cause,
         (unix_timestamp(resumed_at)
          - unix_timestamp(stopped_at)) / 3600.0 AS away_hrs
  FROM ops.cdc_pipeline_stops
  WHERE source_type = 'postgresql'
    AND stopped_at >= current_date() - INTERVAL 90 DAYS
)
SELECT stop_cause,
       count(*)                      AS n,
       avg(away_hrs)                 AS mu_hrs,  -- exponential MLE
       percentile(away_hrs, 0.9)     AS p90_hrs
FROM stops GROUP BY stop_cause;

SELECT width_bucket(wal_gb_per_hr, 0, 10, 3)   AS rate_tier,
       width_bucket(free_disk_gb, 0, 600, 3)   AS disk_tier,
       count(*) / sum(count(*)) OVER ()        AS p_cell
FROM ops.cdc_source_snapshots GROUP BY 1, 2;

Python: score each guard

import numpy as np
rng = np.random.default_rng(102)

def away(mu, u):            # inverse CDF, exponential
    return -mu * np.log1p(-u)

def simulate(H, n, cells, causes, T_min=60, k=50):
    c = rng.choice(len(cells), n, p=cells.p)
    rate, disk = cells.rate[c], cells.disk[c]
    stops = np.floor(np.log(rng.random(n))
                     / np.log(1 - 0.75)).astype(int)
    idx = np.repeat(np.arange(n), stops)
    cause = rng.choice(len(causes), idx.size, p=causes.p)
    t = away(causes.mu[cause], rng.random(idx.size))
    fill = disk[idx] / rate[idx] - T_min / 60
    full = fill < np.minimum(t, H)
    refresh = t > H
    return 1000 * (k * full.sum() + refresh.sum()) / n

best = min([2, 4, 6, 8, 12, 24, 48],
           key=lambda H: simulate(H, 8000, cells, causes))
